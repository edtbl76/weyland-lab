The four principles — how the mesh is defined

Data mesh is an organizing idea before it is a stack. Here is each principle and the concrete thing in weyland that satisfies it.

Principle 01

Domain-oriented ownership

Two bounded domains — music and health — each own their raw → silver → gold assets, schemas, and pipelines end to end (datasets_music.* / datasets_health.*, per-domain Dagster jobs, per-domain keyspaces/DBs across the polyglot stores). No central data team owns the pipelines.

datasets → lakehouse

Principle 02

Data as a product

Nine DataHub Data Products (Spotify Audio, Chronic Health Trends, Genre Classifier, Model-Eval Leaderboard, AI-Dev Usage…), each versioned (Nessie for tables, lakeFS for files), documented, quality-checked, and discoverable — treated as products with owners and contracts, not incidental tables.

catalog emit model catalog

Principle 03

Self-serve data platform

One platform (L1–L8) any domain consumes without a bottleneck team: land → transform → serve → consume. Run-mode tiering keeps it viable on one node — a lightweight always-on foundation, heavy tiers scaled to zero (KEDA) and woken per job; a Port button scales stores on demand.

pipeline trigger store wake/sleep

Principle 04

Federated computational governance

Governance applied as code, globally, while ownership stays local: DataHub catalog + OpenLineage column/run lineage + Soda quality contracts + Ranger column masking + Keycloak identity — one rule set, computed across both domains.

catalog + assertions
The data-product tenets — FAIR, extended

Principle 02 in practice: a dataset earns the status of product only when it satisfies these seven characteristics. They extend the FAIR principles — Findable, Accessible, Interoperable, Reusable (Wilkinson et al., 2016) — into the data-mesh product baseline, each backed by a concrete weyland mechanism.

1
Discoverable
FAIR · Findable
Registered & searchable — every product is a DataHub entry with domain, glossary & tags.
2
Addressable
FAIR · Findable
A unique, stable address to fetch it — Nessie table refs, lakeFS paths, Trino FQNs (iceberg.dbt.mart_*).
3
Understandable
FAIR · Reusable
Self-describing — schema, docs & semantics travel with it (dbt descriptions + DataHub docs + Cube definitions).
4
Trustworthy & truthful
FAIR · Reusable
Stated, provable quality & freshness — Soda assertions + dbt tests + OpenLineage lineage.
5
Natively accessible
FAIR · Accessible
Consumable in each user's native mode — Trino SQL · Cube REST/GraphQL · Feast features · lakeFS files.
6
Interoperable
FAIR · Interoperable
Global standards so products compose across domains — Iceberg/Arrow formats · ODCS contracts · shared keys.
7
Secure & governed
FAIR · Accessible
Access controlled at the product — Keycloak identity + Ranger column masking · policy, not perimeter.
The eight-layer architecture — raw data to data products

The self-serve platform, layer by layer (the B1 build order: storage → federation → transform → catalog → governance → analytics → BI → data science). Solid chips are live; dashed are on-demand (scaled to zero until triggered).

L1

Storage / Data-product layer

the substrate — versioned by data type

Object store + ACID tables. Versioning is split by type: Nessie git-branches Iceberg tables; lakeFS versions files (raw corpora, ML datasets, model artifacts) — complementary.

Query / Federation

one SQL across everything

Governance / Security

authz · quality · identity — federated

The computational-governance layer: Ranger masks Trino columns on the data plane; OPA/Gatekeeper guards the control plane; Soda scans quality into DataHub assertions; Keycloak is the single identity every policy binds to.

A headless semantic layer over the marts — one metric definition, consumed as SQL / REST / GraphQL — plus metrics-as-code in dbt. An app, an agent, or a BI tool all get the same governed numbers.
