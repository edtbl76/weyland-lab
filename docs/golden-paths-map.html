Golden Paths — one contract, many frameworks

A golden path is a blessed, paved-road service template per language/framework — runnable · ephemeral · extendable. Every one conforms to a single framework-agnostic contract (the altitude); the framework lives beneath it, so a language has several golden paths all conforming. Each is both the template a real service scaffolds from (scripts/new-service.sh <path> <name>) and the CI lane's build-infra fixture — they replaced the B88 hello fixtures. Proof is not "tests pass" but the built image serves the contract in-cluster: golden-path-smoke builds each via buildkitd, runs a run-to-completion Job under a dedicated SA, curls /hello, and tears it down. Design: docs/design/golden-paths.md.

How a path is exercised

Scaffold →

new-service.sh <path> <name> copies the golden path (minus build output + the selfcheck probe), rewrites the golden-* token, and prints the onboarding declaration — a real service that passes the B154/B155 gates by construction.

Fixture → lanes

Each path is its lane's fixture: run-lang-tests.sh (test + deliberate-fail selfcheck + coverage ratchet) and run-lang-scan.sh (per-language scanners) — every language gets both.

→ golden-path-smoke

Builds each image via buildkitd from an isolated context, runs a run-to-completion Job (ns golden-paths, SA golden-path-runner), curls the contract, tears it down. Fail-closed: exit 2 build, 1 smoke. Scope one language: --var GOLDEN_PATH_ONLY=<path>.
