# Connected Vehicle

## What It Is
Connected vehicle platforms are the cloud-side infrastructure that ingests, processes, and acts on data from vehicles — and delivers services and software updates back to vehicles. They span telematics (real-time vehicle state, location, diagnostics), OTA software update management, remote services (remote start, lock/unlock, climate precondition), and the data pipelines that feed engineering, operations, and customer-facing applications.

## Why It Matters in Automotive
Connectivity is the enabling layer for the software-defined vehicle — without a reliable, secure bidirectional cloud connection, OTA updates, remote services, and real-time analytics are impossible. Vehicle data is also commercially valuable: warranty analytics, usage-based insurance, fleet management, and predictive maintenance all depend on the telematics data stream. The data volumes are substantial — a connected vehicle generates gigabytes of data per day; a fleet of millions requires serious data engineering.

## Key Concepts
- **TCU (Telematics Control Unit)**: The embedded module in the vehicle responsible for cellular connectivity, GPS, and communication with the vehicle's data bus. Typically the primary vehicle-to-cloud gateway.
- **Vehicle Data Bus (CAN, Ethernet)**: The internal communication network of the vehicle. CAN bus is the legacy standard (J1939 for heavy vehicles). Automotive Ethernet (100BASE-T1, BroadR-Reach) is the standard for high-bandwidth ADAS and infotainment. Data from ECUs is extracted via the TCU or a dedicated gateway.
- **Telematics Data**: Vehicle state signals transmitted to the cloud — location, speed, odometer, fuel level, battery state, fault codes (DTCs), driver behavior, HVAC state. Signal definitions vary by OEM and are often proprietary.
- **DTC (Diagnostic Trouble Code)**: Standardized (OBD-II) or OEM-proprietary fault codes generated by ECUs when they detect a fault. Critical for warranty analytics and remote diagnostics.
- **OTA (Over-the-Air Update)**: Remote software update of vehicle ECUs and systems. Requires a campaign management system (who gets which update, when, under what conditions), secure delivery (code signing, encrypted transport), and robust rollback capability.
- **Vehicle Shadow / Device Twin**: A cloud-side representation of the vehicle's current and desired state. Enables asynchronous command delivery (send a command; execute when vehicle connects) and state synchronization.
- **MQTT / AMQP**: Common messaging protocols for vehicle-to-cloud telemetry. MQTT is preferred for constrained connectivity (low bandwidth, intermittent connection).
- **V2X (Vehicle-to-Everything)**: Adds real-time communication with infrastructure and other vehicles — safety warnings, traffic signal phase and timing, cooperative lane changes. DSRC (802.11p) and C-V2X (cellular) are competing standards; C-V2X (via 5G NR-V2X) is the trajectory.

## Common Patterns / Gotchas
- **Vehicle data semantics are proprietary.** OBD-II standardizes fault codes, but most meaningful vehicle signals (battery state, transmission mode, ADAS state) are in OEM-proprietary CAN messages. Access requires OEM data licensing or a direct OEM integration agreement.
- **Connectivity is intermittent.** Vehicles go through tunnels, garages, and areas with poor cellular coverage. Design all vehicle communication for eventual consistency — commands must queue, data may arrive late or out of order.
- **OTA update failure handling is safety-critical.** A failed partial update that leaves an ECU in an indeterminate state is a vehicle safety risk. Rollback, integrity verification, and pre-conditions (battery level, vehicle stationary) must be designed before any OTA capability is considered production-ready.
- **Data volumes require purpose-built pipelines.** A million-vehicle fleet sending telemetry every 30 seconds generates billions of events per day. Standard event processing architectures scale here, but must be designed for it — not adapted from lower-volume systems.
- **Privacy regulation applies to location and driver behavior data.** GDPR, CCPA, and emerging automotive-specific regulations govern how vehicle location and behavior data is stored, used, and shared. Data residency and consent management must be in scope.
- **Cellular connectivity cost is a design constraint.** Data plans for embedded cellular add up at scale. Optimize payload size, sampling frequency, and edge processing to minimize cellular data usage.

OTA update rollback and integrity verification must be designed before any OTA capability ships — a failed update that bricks an ECU is a recall event, not a software bug. Design all vehicle communication as eventually consistent from day one; vehicles are offline more than you expect. ## Solutions Context
**Typical engagement patterns**: Telematics ingestion platform, OTA update infrastructure, remote vehicle services, fleet management platform, vehicle data analytics, connected vehicle SDK.

**Common scope anchors**: TCU integration and data ingestion pipeline, OTA campaign management and delivery, vehicle shadow/device twin, DTC analytics and remote diagnostics, privacy and consent management, V2X integration.

**Risk factors**: OEM data licensing and access agreements are prerequisites that can delay project start. OTA safety validation (especially for safety-critical ECUs) adds significant testing scope. Data volume estimation for large fleets is frequently underestimated.
