# Supply Chain Security

## What It Is
The set of practices that protect the software delivery pipeline itself — from source code through dependencies, build systems, and artifacts — against tampering, malicious packages, and compromised tooling. Supply chain attacks target the tools and dependencies that developers trust: a compromised npm package, a backdoored build server, or a tampered container image can ship malicious code into production without the application team being aware. Supply chain security is about ensuring that what you built is what gets deployed, and that what you pulled in as a dependency is what it claims to be.

## When to Apply
- Any production system (supply chain attacks are indiscriminate)
- Before publishing packages or container images externally
- When evaluating third-party build tooling, CI systems, or package registries
- Systems with compliance requirements (NIST SSDF, SOC 2, FedRAMP)

## Key Concepts
- **Dependency Confusion**: An attacker registers a public package with the same name as an internal private package. When the package manager checks public registries first, it pulls the malicious version. Mitigation: namespace private packages (`@company/pkg`), configure registry resolution order, use private proxies
- **Typosquatting**: Malicious packages with names similar to popular packages (`reqeusts` vs `requests`). Mitigation: pin exact dependency versions, review new dependencies before adding them
- **Compromised Packages**: Legitimate packages that are later modified to include malicious code (via compromised maintainer accounts or takeover of abandoned packages). Mitigation: pin exact versions in lockfiles, subscribe to security advisories, use automated CVE scanning
- **SBOM (Software Bill of Materials)**: A machine-readable inventory of all components in a software artifact — direct and transitive dependencies, versions, and licenses. SBOMs enable rapid impact analysis when a CVE is disclosed. Generate with Syft, Trivy, or CycloneDX. Required for US federal procurement (Executive Order 14028)
- **Artifact Signing**: Cryptographically sign build artifacts (container images, packages) to prove they came from your build system and were not tampered with in transit. Tools: Sigstore/Cosign for container images, PGP for packages
- **SLSA (Supply-chain Levels for Software Artifacts)**: A framework of security levels for software supply chains. Higher SLSA levels require hermetic builds, provenance attestation, and two-party review. Backed by Google and the OpenSSF
- **Build Provenance**: Metadata that records where, when, and how an artifact was built — which source commit, which builder, which dependencies. Enables verifying an artifact's origin. GitHub Actions supports SLSA provenance generation
- **Secure CI/CD**: CI systems are high-privilege environments. Treat CI credentials as secrets, pin action versions (use SHA rather than tag), restrict OIDC token permissions, and audit third-party GitHub Actions before use
- **Container Base Image Security**: Use minimal base images (distroless, Alpine) to reduce attack surface. Pin base image digests. Scan images for CVEs. Rebuild regularly to pick up OS-level patches

## In Practice
Method pins all dependency versions in lockfiles. Container images are signed with Cosign and pushed to ECR with SBOM attestations generated by Trivy. GitHub Actions pin third-party actions by commit SHA. OIDC tokens are scoped to minimum permissions per job. Snyk monitors open source dependencies. SBOMs are generated as part of the build pipeline for compliance artifacts.

## Engineering Knowledge Statement
💡 **Engineering Knowledge — Supply Chain Security**: The weakest link in your supply chain is often a dependency you didn't write and didn't review. Pin dependencies and use lockfiles to prevent surprise updates. Generate SBOMs so you know what's in your artifacts. Sign container images with Cosign to ensure what's in the registry is what you built. In CI, pin third-party actions by SHA — not by a mutable tag — to prevent a compromised action from executing in your pipeline. SBOM generation is now required for government contracts and is rapidly becoming standard practice. → `engineering-knowledge-repository/supply-chain-security.md`
