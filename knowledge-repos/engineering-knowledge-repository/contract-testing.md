# Contract Testing

## What It Is
A testing approach where the contract between a service provider and its consumers is explicitly defined and verified by both sides — independently. The consumer defines what it expects from the provider; the provider verifies it can fulfill those expectations. Neither side needs the other to be running during the test. Most commonly implemented with Pact.

## When to Apply
- Microservices or distributed systems with multiple teams owning separate services
- When integration tests are slow, flaky, or require complex environment setup
- When API changes between teams frequently cause surprises
- When you need confidence that a service change won't break its consumers before deploying

## When Not to Apply
- Monolithic systems where all code is tested together — integration tests cover this adequately
- Simple internal APIs with a single consumer and a single team — the overhead is not justified
- Third-party APIs you don't control — you can test your client code, but the provider won't run contract tests

## Key Concepts
- **Consumer-Driven Contract**: The consumer defines the contract — what fields it uses, what responses it expects. The provider verifies against it.
- **Pact**: The most widely used contract testing framework. Pact files are generated by consumer tests and published to a Pact Broker; provider tests verify against them.
- **Pact Broker**: A repository for Pact files — enables teams to share contracts and track verification status.
- **Can-I-Deploy**: A Pact Broker command that checks whether it is safe to deploy a version of a service given the current contract verification status.
- **Provider State**: A mechanism for the consumer to tell the provider what state to be in before verifying a specific interaction (e.g., "user exists", "cart is empty").

## In Practice
Contract testing surfaces in Infrastructure Design for microservices engagements — it replaces or supplements expensive end-to-end integration environments. It is most valuable when multiple teams own separate services and API changes are frequent. Start with the most critical service boundaries. A Pact Broker (self-hosted or PactFlow) is needed for team-scale contract sharing.

## Engineering Knowledge
💡 **Engineering Knowledge — Contract Testing**: Integration environments are slow and fragile. Contract testing verifies that your service and its consumers agree on the API — without either side needing to be running. Define consumer expectations as tests; verify provider compliance in CI.
